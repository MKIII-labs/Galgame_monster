# 工作流编排

先判断是否真的需要工作流，再选 DAG、脚本还是直接并行；不要用工作流包装一次普通调用。

## 何时用

- 3 步以上、有前后依赖的任务，例如「探索 → 改多个文件 → 跑测试 → 校验 → 汇总」
- 需要对同一模板批量扇出（每个文件 / 每个 URL / 每个子任务）
- 需要循环直到条件满足，或按条件走不同分支
- 任务可能中断，需要断点续跑
- 需要多个子代理按流水线串行交接

## 不适用

- 单次工具调用，或 2–3 次无分支的顺序调用
- 纯文本生成、写作、分析报告（瓶颈是模型思考，不是工具编排）
- 任务范围还不清楚，需要先问用户
- 只需要简单并行读取，直接用并行工具调用或 `agent(action=explore)` 即可

## 核心步骤

1. **先判断形态**：能用 1–2 次直接工具调用完成，就不要用工作流。
2. **选对工具**：
   - `run_workflow`：DAG 编排。节点类型 `tool / command / script / explore / verify / final / loop / map / condition`；用 `needs` 组依赖，用 `{{id.output}}` 引用产物。
   - `run_workflow_script`：需要变量、循环、动态扇出或 Python 逻辑时用；脚本里用 `wf.call` / `wf.parallel` / `wf.workflow` / `wf.agent` / `wf.pipeline` / `wf.log`。
   - 直接并行工具 / `agent(action=explore)`：只读、互不依赖的简单并行。
3. **写清节点契约**：每个节点要有输入、输出、失败策略（`on_error`、`retries`、`if_exists`、`timeout`）；需要汇总时用 `final` 节点或 `template`。
4. **控制并发与写入**：只读节点可以并行；写文件 / 跑命令按依赖串行，避免同一文件被多个节点同时写。
5. **给循环设上限**：`loop` 必须写 `max_iterations` 或 `until`，不要无限循环。
6. **执行与检查**：执行后用 `workflow_status` 查看每个节点状态与输出；中断后用 `workflow_resume` 续跑；取消用 `workflow_cancel`。
7. **验收后再汇报**：失败节点不能当成功跳过；`final` 汇总要引用真实节点输出，不要编造。

## 输出格式

- 工作流 id（`wf_...`）
- 节点状态：完成 / 失败 / 跳过
- 关键产物路径或摘要
- 失败节点与原因，以及下一步是续跑、改节点还是人工处理

## 失败处理

- 节点失败：先看错误与已完成节点；能续跑就 `workflow_resume`，不能续跑就缩小范围或改节点后重跑。
- 循环不收敛：检查 `until` 条件与 `max_iterations`，不要靠继续重试碰运气。
- 写入冲突：把写节点改成串行，或拆成不同文件 / 不同工作流。
- 依赖节点失败：根据 `on_error` 决定停止还是继续；不要把依赖失败的下游节点标成成功。
- 输出缺失：检查 `{{id.output}}` 引用名是否与节点 `id` 一致。

## 常见错误

- 用工作流包装一次普通工具调用
- 没有 `needs`，导致节点并发写同一文件
- 循环没有上限或 `until` 永远为真
- 不检查节点输出就直接 `final` 汇总
- 失败节点跳过不报，最后声称全部完成
- 脚本里重复实现已有工具能力，而不是调用 `wf.call`
