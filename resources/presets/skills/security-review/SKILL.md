# 安全审查

找出**可被利用**的安全问题，按可利用性与影响排序；只报能给出触发路径的结论。

## 何时用

- 用户要求「安全审查 / 渗透视角看一遍 / 有没有漏洞」
- 改动涉及：认证鉴权、权限校验、文件路径与上传、命令 / SQL / 模板拼接、
  反序列化、外部 URL 抓取、密钥与配置、跨端数据写入
- 上线前的最后一道安全检查

不适用于：普通代码质量审查（走「代码审查」技能）、纯功能实现、性能优化。

## 核心步骤

1. **定边界**：先明确入口（HTTP 路由 / 工具参数 / 文件内容 / 第三方回调）、
   信任边界（谁能调用）、以及受保护资产（密钥、用户数据、宿主机）。
2. **找汇聚点**：把外部输入追到危险操作——`exec` / 子进程、`os.remove`、
   `open(..., 'w')`、SQL 拼接、`eval` / `pickle.loads`、`requests.get`、
   `innerHTML`、路径拼接。追不到执行点的不报。
3. **验控件**：每个汇聚点检查：输入校验（白名单 / 类型 / 长度）、
   路径归一化与前缀校验、命令是否数组传参、SQL 是否参数化、
   权限是否在服务端校验（不是前端隐藏按钮）。
4. **查秘密**：日志 / 报错 / 响应里是否回显密钥、令牌、绝对路径；
   配置是否被打进仓库或产物；`.env`、私钥、cookie 是否可被读取或外传。
5. **排误报**：确认攻击者真的能控制该输入、真的能到达该代码、
   影响真实存在（不是「理论上」）。每条给：**位置（文件:行号）→ 触发路径 → 影响 → 修复建议**。

## 严重度口径

- 严重：未授权远程执行 / 任意文件读写 / 密钥泄露 / 鉴权绕过
- 高：越权读写他人数据、SSRF 打内网、命令或 SQL 注入需登录触发
- 中：需要用户交互的 XSS、信息泄露、权限校验缺失但影响有限
- 低：加固建议（缺安全头、日志过多、弱默认值）

## 输出

按严重度分组，每条一行标题 + 触发路径 + 修复建议；没有发现时明确说
「在本次审查范围内没找到可利用问题」，并列出**没覆盖**的范围（例如未审计依赖、未跑动态测试）。

## 纪律

- **只读**：不修改代码、不执行利用脚本、不访问外部目标。
- 不编造 CVE / 依赖漏洞；依赖风险只说「需用 `pip-audit` / `npm audit` 核实」。
- 不把「风格问题」「潜在重构」混进安全结论。
