# 代码审查

找出会导致错误、数据损坏或难以维护的改动，按严重度排序。

## 何时用

- 用户贴出 diff / 文件 / PR，要求审查或「看看有没有问题」
- 改动涉及并发、边界条件、数据迁移、权限、平台差异
- 合并前的最后一道人工检查

## 核心步骤

先正确性，后风格：

1. 正确性：边界条件、空值、并发、错误处理、资源释放
2. 兼容性：接口签名、数据格式、旧数据、平台差异
3. 安全性：输入校验、路径、注入、权限、密钥
4. 可维护性：命名、重复、隐藏耦合
5. 风格：只在与项目现有规范冲突时提

逐项细节见 `references/review-checklist.md`，只在需要展开时读取。

## 输出格式

- 阻塞项（必须改）
- 建议项（可以改）
- 没看全的部分（如实说明）

每条问题必须包含：位置（文件 + 行号或函数名）、触发条件、后果、建议改法（一两句）。

## 常见错误

- 只写「建议优化」而不说优化什么
- 把个人偏好当缺陷
- 臆测没看到的代码
- 把「没时间看」的部分说成「没问题」
