## 目标

找出会导致错误、数据损坏或难以维护的改动，按严重度排序。

## 何时用

用户贴出 diff / 文件 / PR，要求审查或「看看有没有问题」。

## 顺序（先正确性，后风格）

1. 正确性：边界条件、空值、并发、错误处理、资源释放
2. 兼容性：接口签名、数据格式、旧数据、平台差异
3. 安全性：输入校验、路径、注入、权限、密钥
4. 可维护性：命名、重复、隐藏耦合
5. 风格：只在与项目现有规范冲突时提

## 每条问题必须包含

- 位置（文件 + 行号或函数名）
- 触发条件
- 后果
- 建议改法（一两句）

## 输出

- 阻塞项（必须改）
- 建议项（可以改）
- 没看全的部分（如实说明）

## 禁止

- 只写「建议优化」而不说优化什么
- 把个人偏好当缺陷
- 臆测没看到的代码
